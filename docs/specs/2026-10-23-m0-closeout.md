# M0 收尾：Java↔gateway 契约 v1 与 RAG 选型

日期：2026-10-23
状态：待实现
相关决策：ADR-0004、ADR-0005（Proposed）、ADR-0006

## Problem Statement

M0 的目标是用最小闭环消除两类不确定性：pi 集成方式与 RAG 技术选型。pi 集成的三个风险点（prompt 整体替换、工具白名单、SSE 事件流）已经用真实模型验证；但契约仍是 v0——gateway 把 pi 的内部事件名原样透传给 Java 和 web，pi 一升级，业务层和前端就要跟着改。

同时，会话生命周期不幂等（创建重试会撞 409）、身份只在创建时传递（后续 prompt 不校验归属）、工具回调不带身份（Java 无法强制按用户隔离和审计）、每轮没有唯一终态（前端要自己兜底）。RAG 的向量库、embedding 与 rerank 通路也尚未决策。

如果先写 M1 的持久化和摄取管线，这些不确定性会直接变成返工。因此先把契约冻结成 v1，并用一次 spike 把 RAG 依赖选型钉死。

## Solution

两件事并行：

1. **冻结 Java↔gateway 契约 v1**：归一化领域事件、唯一终态、显式中断、幂等会话生命周期、统一身份 header、稳定错误码、固定 SSE 帧格式；用一份共享 fixture 作为两侧测试的唯一事实源。
2. **RAG 选型 spike**：用 Qdrant + 可配置的 OpenAI 兼容 embedding/rerank 端点，跑通「100 页 PDF 摄取 → 检索 → 重排 → 引用」闭环，产出实测数据，把 ADR-0005 从 Proposed 转成 Accepted。

两者都不实现 M1 的业务纵深（持久化、认证、摄取管线、沙箱执行器），但会把它们的接口边界定死。

## User Stories

1. 作为终端用户，我希望回复逐字出现，这样我不用等待整段生成完才看到内容。
2. 作为终端用户，我希望看到模型的推理摘要，这样我能判断它是否理解了问题。
3. 作为终端用户，我希望看到工具调用参数逐字生成、执行阶段和输出进度，这样长时间的工具调用不会像卡死。
4. 作为终端用户，我希望点击停止后回复立即停止，不再继续消耗 token。
5. 作为终端用户，我希望网络断开后重新打开会话能看到已经产生的部分回复，而不是空白、丢失或重复。
6. 作为终端用户，我希望自己的知识库内容永远不会出现在别人的回答里。
7. 作为前端开发者，我希望只处理一组稳定的领域事件，不需要理解 pi 的内部事件结构。
8. 作为前端开发者，我希望每轮只有一个明确的结束事件，从而把「思考中/工具中/已完成/已中断/失败」的状态机写简单。
9. 作为业务层开发者，我希望会话创建可以安全重试，不会产生重复会话或孤儿会话。
10. 作为业务层开发者，我希望每次工具回调都带齐用户、会话、轮次、执行和工具调用 ID，从而正确隔离数据并写审计。
11. 作为业务层开发者，我希望每轮有一个确定的终态和稳定的错误码，从而决定是否重试、如何落库。
12. 作为业务层开发者，我希望同一轮消息的重复投递不会产生重复行。
13. 作为业务层开发者，我希望断流时能明确知道「没有收到终态」，从而把已产生的部分回复落成可展示的历史。
14. 作为 gateway 开发者，我希望同一会话的第二次 prompt 被明确拒绝，而不是静默排队挂起一个 SSE 连接。
15. 作为 gateway 开发者，我希望会话 ID 由业务层生成，gateway 不承担业务 ID 语义。
16. 作为 gateway 开发者，我希望 pi 升级只影响事件翻译器和它的测试，不影响 Java 与 web。
17. 作为安全负责人，我希望身份只从受信任的 header 注入，模型无法通过工具参数伪造用户身份。
18. 作为运维，我希望 Java 启动时发现契约主版本不匹配就立即失败，而不是运行到一半才报错。
19. 作为运维，我希望长回复不会被反向代理的空闲超时切断。
20. 作为运维，我希望断连的会话不会留下持续消耗资源的后台任务或孤儿容器。
21. 作为 RAG 负责人，我希望向量库和 embedding/rerank 的选型有实测数据支撑，而不是凭直觉。
22. 作为 RAG 负责人，我希望明确知道更换 embedding 模型需要全量重建索引，以及重建的触发方式。
23. 作为 RAG 负责人，我希望外部免费/低价模型限流或超时时，摄取任务可以重试并断点续跑。
24. 作为测试工程师，我希望两侧用同一份契约 fixture 验证行为，不依赖真实模型或外部网络。
25. 作为测试工程师，我希望检索隔离、rerank 降级、断流兜底这些关键行为都有可重复的自动化测试。
26. 作为未来维护者，我希望文档记录为什么不用透传、pgvector、Milvus 和 Redis 向量检索，避免重复讨论。

## Implementation Decisions

### 契约 v1：事件模型

Java 与 web 只依赖以下领域事件。pi 的原始事件仅进入 gateway 结构化日志，不对线上暴露。

| 事件 | data | 说明 |
|---|---|---|
| `run_started` | `{ runId, turnId, sessionId, contractVersion }` | 每轮第一帧，`seq = 1` |
| `thinking_delta` | `{ delta }` | 模型推理增量，展示用 |
| `text_delta` | `{ delta }` | 正文增量 |
| `tool_call_delta` | `{ toolCallId, name, delta }` | 模型生成工具参数的增量，展示用 |
| `tool_call` | `{ toolCallId, name, args }` | 参数生成完毕、工具开始执行 |
| `tool_progress` | `{ toolCallId, name, kind: "phase"\|"stdout"\|"stderr", phase?, chunk? }` | 工具执行进度，展示用；`chunk` ≤ 2KB |
| `tool_result` | `{ toolCallId, name, isError, durationMs, content }` | 最终工具结果；`content` 按 64KB 截断 |
| `message_end` | `{ seqInTurn, role: "assistant", text, thinking, toolCalls, usage, stopReason }` | 一条 assistant 消息的持久化单元；工具循环会产生多条 |
| `compaction` | `{ reason, tokensBefore, tokensAfter }` | 上下文压缩发生 |
| `retry` | `{ attempt, maxAttempts, delayMs, message }` | 自动重试进行中，不是终态 |
| `run_settled` | `{ status: "completed"\|"aborted"\|"error", error?: { code, message, retryable } }` | 每轮唯一终态，之后流关闭 |

- **不进 v1**：`tool_execution_update` 的原始结构、`queue_update`、`session_info_changed`、`thinking_level_changed`、`bash_execution_update`。
- `usage` 采用 pi 的完整字段：`input`、`output`、`cacheRead`、`cacheWrite`、`reasoning`、`totalTokens`、`cost`。
- `tool_progress` 只用于展示，不进入模型上下文；模型只认 `tool_result`。
- `kb_search` 不产生假进度（检索没有有意义的中间输出）；`run_code` 在 M1 改成流式回传后发出 `phase`/`stdout`/`stderr`。
- 契约只做加法演进；删除字段或改变语义必须升主版本。

### 契约 v1：SSE 帧与连接语义

- 帧格式：`id: <runId>:<seq>`、`event: <领域事件名>`、`data: <单行紧凑 JSON>`，空行结束。
- `seq` 每轮从 1 单调递增；`run_started` 为 1，`run_settled` 为最后一帧。
- 心跳：每 15 秒发送 `: ping` 注释帧，不占 `seq`、不产生事件。
- 响应头：`content-type: text/event-stream; charset=utf-8`、`cache-control: no-cache, no-transform`、`x-accel-buffering: no`。
- **不支持回放**：忽略 `Last-Event-ID`；连接断开即本轮结束，历史从业务层消息投影读取，不从事件流重放。
- **一个会话同时只有一个进行中的 Run**：收到第二个 prompt 时返回 `409 RUN_IN_PROGRESS`，不排队、不挂起第二个 SSE 流。
- HTTP 200 写出后，第一帧必须是 `run_started`；会话不存在、归属不符、已有 Run 等错误在写 SSE 头之前返回 JSON 错误。
- `run_settled` 发出后 gateway 立即关闭流，不再发送任何事件。

### 契约 v1：会话生命周期与身份

| 方法 | 路径 | 语义 |
|---|---|---|
| `GET` | `/health` | `200 { ok, contractVersion: "1", sessions }` |
| `PUT` | `/sessions/:id` | 幂等创建：不存在则创建；已存在且归属相同返回 `created: false`；归属不同返回 `409 SESSION_CONFLICT` |
| `POST` | `/sessions/:id/prompt` | body `{ text, turnId }`，返回 SSE；不存在 `404`，归属不符 `403`，已有 Run `409 RUN_IN_PROGRESS` |
| `POST` | `/sessions/:id/abort` | `202`；空闲时 `409 NO_ACTIVE_RUN`；归属不符 `403` |
| `DELETE` | `/sessions/:id` | 幂等删除，`204`；归属不符 `403` |

- **身份统一放 `X-User-Id` header**（比讨论中的 PUT body 更一致，语义不变）；Java 与 gateway 之间仍用共享 Bearer token。
- 会话 ID 由 Java 生成，gateway 不生成 ID。
- 所有操作校验 header 中的 userId 与会话绑定一致，不一致返回 `403 USER_MISMATCH`。
- 显式中断是用户「停止」的唯一协议动作；客户端断连仍触发 abort，作为 ADR-0002 的兜底。
- `PUT` 返回后承诺会话可继续 prompt；如何恢复（pi session 存储、未来共享存储）是 gateway 实现细节。

### 契约 v1：工具回调

- gateway 调用 Java 与沙箱服务时注入：
  `X-User-Id`、`X-Session-Id`、`X-Turn-Id`、`X-Run-Id`、`X-Tool-Call-Id`、`X-Request-Id`。
- **身份只走 header，绝不放进工具参数**；模型不能通过 `query`、`code` 等字段伪造用户身份。
- `X-Request-Id` 由 Java 在发起 prompt 时生成，gateway 一路透传到工具回调与日志。
- `kb_search`：body `{ query, topK }`；响应 `{ passages: [{ passageId, documentId, seq, title, content, score, reranked }] }`。
- `run_code`：M1 改为 SSE，事件 `started { execId }` → `phase/stdout/stderr` → `result { exitCode, durationMs, timedOut, truncated }`；任何上游断连都杀容器，并写一条 `status=aborted` 的执行记录。
- 工具回调失败返回统一的错误 envelope；gateway 将其转成 `isError: true` 的 `tool_result`，保留 `code` 供日志。

### 契约 v1：错误与版本

所有非流式错误统一为：

```json
{ "error": { "code": "SESSION_NOT_FOUND", "message": "...", "retryable": false } }
```

| code | HTTP | 场景 |
|---|---|---|
| `INVALID_REQUEST` | 400 | 参数缺失或格式错误 |
| `UNAUTHORIZED` | 401 | 共享 token 不正确 |
| `USER_MISMATCH` | 403 | 身份与会话归属不符 |
| `SESSION_NOT_FOUND` | 404 | 会话不存在 |
| `SESSION_CONFLICT` | 409 | PUT 时会话归属不同 |
| `RUN_IN_PROGRESS` | 409 | 同一会话已有进行中的 Run |
| `NO_ACTIVE_RUN` | 409 | 空闲时调用 abort |
| `UPSTREAM_UNAVAILABLE` | 503 | gateway 无法连接业务层或沙箱 |
| `INTERNAL` | 500 | 未分类错误，message 不含堆栈 |

- 流式错误不另发 `error` 事件，一律由 `run_settled.error` 收尾。
- Java 启动时检查 `/health.contractVersion` 主版本，不匹配即拒绝启动。
- `run_started.contractVersion` 供滚动升级时发现旧 gateway。

### 持久化边界

- **只有 Java 写业务 MySQL**；gateway 不碰业务库，pi 不做业务。
- **pi 的 session 存储是引擎上下文的唯一来源**；MySQL 消息投影只服务展示、历史与统计，不用来重建 pi 上下文。
- 三个持久化单元：用户消息（prompt 前写入，`delivery_status = pending`）、`message_end`（assistant 消息，`status = complete`）、`tool_result`（role=tool）。delta 与进度事件不落库。
- `turnId` 是幂等键：Java 生成，随 prompt 发送，gateway 在 `run_started`/`run_settled` 回显；消息唯一键包含 `(session_id, turn_id, seq_in_turn)`。
- 用户消息投递状态：`pending` → `sent`（收到 `run_started`）；gateway 不可达时 `failed`，允许用同一 `turnId` 重试。
- assistant 消息状态：`complete` / `partial` / `error`。
- Java 的 SSE 读取循环结束时若未收到 `run_settled`，合成 `STREAM_INTERRUPTED`，把已累积增量落成 `partial`，避免「用户消息在、回复永远 pending」。
- 断连按 abort 处理（Q10 决定）：省 token、不留后台任务；重连从消息投影读历史，不续流。

### RAG 选型与配置

- 向量库直接选 **Qdrant**，不做三选一 benchmark；单 collection `kb_passages`，payload 含 `user_id`、`document_id`、`seq`、`text`，对 `user_id` / `document_id` 建 payload 索引。
- 检索必须用 Qdrant 服务端过滤 `user_id`，不能把用户过滤拼进查询字符串；MySQL 仍是文档元数据与原文的真相源。
- embedding / rerank 走**可配置的 OpenAI 兼容端点**，默认请求形状：
  - `POST {base-url}/embeddings` `{ model, input: [...] }` → `data[].embedding`、`data[].index`
  - `POST {base-url}/rerank` `{ model, query, documents, top_n }` → `results[].index`、`results[].relevance_score`
  - TEI 等不兼容服务通过 adapter 支持。
- 配置项（Java 侧，环境变量注入）：
  - `EMBEDDING_BASE_URL` / `EMBEDDING_API_KEY` / `EMBEDDING_MODEL` / `EMBEDDING_DIM` / `EMBEDDING_BATCH_SIZE`
  - `RERANK_ENABLED` / `RERANK_BASE_URL` / `RERANK_API_KEY` / `RERANK_MODEL` / `RERANK_TOP_N`
- **维度锁死**：启动时校验 `EMBEDDING_DIM` 与 collection 维度一致，不一致拒绝启动；换 embedding 模型必须全量重建索引。
- rerank 流程：向量召回 top-20 → rerank 取 top-5；`RERANK_ENABLED=false` 时按向量分数返回并标记 `reranked: false`。
- **凭证边界**：embedding/rerank 的 key 是 encoder 推理凭证，放在业务层环境变量/密钥管理；生成式 LLM 凭证仍只存在 pi 的凭证存储，gateway 是唯一生成式模型通路。

### RAG spike 范围

1. 语料：一份 100 页左右中文 PDF，切成 300–500 个 Passage。
2. 质量：人工标注 20 条查询及期望 Passage，记录「纯向量」与「向量 + rerank」的 `recall@5`、`MRR`。
3. 工程指标：摄取总耗时、embedding 端点 p95、检索 p95、Qdrant 内存占用、单次查询成本估算。
4. 达标线：摄取 ≤ 5 分钟（FR-2 AC1）；`kb_search` 回传 p95 < 500ms（不含代码执行）；rerank 后 `recall@5` ≥ 0.8，未达标则调整模型/切分/召回数并记录。
5. 故障：embedding 端点 429 / 超时 / 500 时重试与断点续跑；检索失败时 `kb_search` 返回明确错误。
6. 隔离：两个 `user_id` 的 Passage 混在同一 collection，确认过滤后互不可见（FR-2 AC3）。
7. 产出：ADR-0005 转 Accepted（或记录否决理由）；实测数据写入选型记录。spike 代码放独立分支，只把 ADR 与结论合回 `dev`。

## Testing Decisions

- **唯一测试缝是 Java↔gateway 的 HTTP 契约**，两侧共用同一份 fixture（`contract/v1/`）作为真相源。
- gateway 侧：把 fixture 中的 pi 事件序列喂给翻译器，断言输出的事件名、`data`、`seq`、终态完全一致（golden test）；不启动真实 pi、不调模型。
- Java 侧：用假 gateway 重放同一份 fixture，断言解析、错误映射、`STREAM_INTERRUPTED` 兜底、身份 header 注入；不依赖真实网络与模型。
- 真实 LLM 冒烟只在契约变更时手工跑，不进 CI（慢、贵、随机）。
- RAG：假 embedding 端点返回确定性向量；Qdrant 用 Testcontainers；覆盖隔离过滤、rerank 降级、限流重试。
- 沙箱：Docker 可用时跑真容器验证隔离参数；CI 不可用时跳过并标注原因，不伪装通过。
- 好测试只断言外部行为：HTTP 状态、SSE 帧、落库行、检索结果；不断言翻译器内部结构、不 mock pi 的内部类。

## Out of Scope

- M1 的持久化实现、认证与多租户、RAG 摄取管线、沙箱执行器与审计、compaction 配置化、画像记忆。
- `tool_progress` 的实际实现（随 M1 的 `run_code` 流式端点落地）。
- gateway 多实例、亲和路由、冷启动恢复压测。
- Qdrant 之外向量库的 benchmark；pgvector / Milvus / Redis Stack 的进一步评估。
- O4（AIO Sandbox 作为独立 workspace 层）。

## Further Notes

- 契约 v1 的决策细节见 ADR-0004；持久化边界见 ADR-0006；RAG 依赖见 ADR-0005。
- 执行顺序：契约 fixture → gateway 翻译与生命周期 → Java 消费方；RAG spike 可并行；CI 卫生在 fixture 落地后接入。
- 主要风险：thinking 内容可能暴露给前端截图；免费 embedding 端点限流/停服；embedding 维度锁死导致换模型成本高；契约翻译器漏字段。缓解分别是默认折叠、重试与可切换端点、启动校验与重建流程、fixture golden test。

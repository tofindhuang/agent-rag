# M1 Closeout 压测（50 并发活跃会话）

日期：2026-10-25
状态：已实现（tickets 01–05 全部 done；结果见 `docs/research/2026-10-25-m1-load-test-report.md`，原始样本见同目录 `-artifacts/`）
关联：`docs/requirements.md` §1.2（M1 目标）、§4（非功能需求）；ADR-0008/0010/0015（gateway 会话池 / 模型凭证 / 限流）

## Problem Statement

M1 的结束条件「单 gateway 实例可支撑 50 并发活跃会话的完整产品功能」目前只有设计依据，没有实测证据；§4 的延迟指标（首 token P95 < 3s 扣除模型自身 TTFB；`kb_search`/`run_code` 回传 P95 < 500ms 不含执行本身）与「任一重启不丢已持久化消息」同样缺验收数据。M1 closeout 需要一次可复现的压测来补齐这些证据。

## Solution

提供一套**临时栈编排 + 压测 harness**：在本机用 docker compose 起全新（空数据卷）的 MySQL/Redis/Qdrant 容器，本地起 Java 与 gateway 进程；harness 以 50 个虚拟用户走**公开 Java HTTP API**（与 web 客户端完全相同的缝）完成注册 → 配置 DeepSeek provider → 建会话 → SSE 多轮对话，混合小规模 `run_code` / `kb_search` 工具路径；并行采样直连 DeepSeek 的流式首 token 基线用于扣除模型自身 TTFB；压测中段对 gateway 做一次滚动重启，验证消息不丢不重。产出 Markdown 压测报告，压完即拆栈（`docker compose down -v`），不触碰任何既有本地数据库。

## User Stories

1. 作为项目 owner，我要「50 并发活跃会话」的实测通过证据，以便宣告 M1 P0 验收完成。
2. 作为项目 owner，我要首 token P95（扣除模型自身 TTFB）的量化数据，以便对照 §4 的 < 3s 指标。
3. 作为项目 owner，我要 `kb_search` 与 `run_code` 回传 P95 的量化数据（不含执行本身），以便对照 §4 的 < 500ms 指标。
4. 作为维护者，我要可复现的一键流程（起栈 → seed → 压测 → 报告 → 拆栈），以便 M2 复测与调优对比。
5. 作为维护者，我要压测中 gateway 重启后已持久化消息不丢不重的实证，以便覆盖 §4 可用性指标。
6. 作为维护者，我要压测绝不写入任何既有本地数据库（只用一次性容器与空数据卷），以便遵守本机 DB 铁律。
7. 作为维护者，我要 DeepSeek key 只经环境变量注入临时进程、不落任何仓库/临时文件、不出现在报告中，以便凭证安全。
8. 作为维护者，我要错误按类别区分统计（硬错误 / 本系统 429 / 上游 provider 429 / 客户端断流），以便定位瓶颈时不受噪音干扰。
9. 作为维护者，我要压测配额调整只作用于临时栈的环境变量，以便正式部署配额不受影响。
10. 作为维护者，我要报告记录环境快照（镜像版本、模型、配额、机器规格），以便日后结果可比。
11. 作为维护者，我要断流后 harness 用 turnId 幂等重试并校验消息不重复，以便真实检验断连恢复语义。

## Implementation Decisions

- **测试缝**：harness 只打 Java 公开 HTTP API（`/api/auth/*`、`/api/models/providers`、`/api/kb/*`、`/api/chat/sessions/*`），即产品真实客户端缝；不直接调 gateway 内部接口。SSE 事件解析遵循 contract v1 事件定义。唯一新增缝是两个外部测试替身（见下）。
- **环境**：一次性 compose 起全新 mysql/redis/qdrant **以及 rabbitmq/silo** 容器（KB 摄取队列与原文对象存储需要；compose 项目名隔离、无持久数据卷）；Java :8080、gateway :3001 本地进程；sandbox 镜像用本机已有 `agent-core-sandbox:python-3.12`（不在运行时构建）。压完 `docker compose down -v` 全量拆除。
- **配额**：临时栈通过 env 调高 `RATE_LIMIT_USER_RPM` / `RATE_LIMIT_USER_TPM` / `RATE_LIMIT_AUTH_IP_RPM`（默认 auth-ip-rpm=10，50 用户批量注册/登录必撞）。限流行为本身已有 server 测试覆盖，本压测不验证限流，目标是并发与延迟。
- **虚拟用户**：50 个测试用户（注册进临时库）。负载构成：40 纯 chat + 5 `run_code` + 5 `kb_search`；每用户默认 3 轮对话，轮间 think-time 3–8s 随机；turn 以 `run_settled` 收尾。
- **模型**：真实 DeepSeek（`https://api.deepseek.com`，`deepseek-chat`）。50 用户配同一 provider key；key 经环境变量注入，来源为用户上一次会话提供的 key（用户已确认复用；收尾时再次提醒轮换）。
- **TTFB 扣除**：harness 内并行基线采样器以同样 key 直连 DeepSeek 流式接口测首 token 时间（约每 5s 一次、贯穿全程），报告给出「原始 P95」与「扣除基线中位/P95 后」两个口径。
- **kb_search 路径**：复用此前 demo 的确定性假 embedding/rerank 服务模式（`demo-embedding` 1024 维 + `demo-rerank`，本地端口，确定性向量保证有命中）；给 5 个 kb 用户各 seed 一份小语料（数篇短文）。报告明确注明 embedding/rerank 供应商真实延迟不在测量内——与扣除模型 TTFB 同理，量的是自身管线开销。
- **run_code 路径**：prompt 引导模型调用 `run_code` 执行毫秒级任务（如 `print`），使「执行本身」可忽略；回传延迟取 `tool_call` → `tool_result` 事件间隔，报告注明方法。
- **重启验证**：压测中段重启 gateway 进程一次：断流用户以原 `turnId` 重发（幂等重试）；重启完成后逐会话 `GET messages` 校验已 settled 消息齐全且无重复——completed turn 的 user 消息恰好一条、assistant 回复存在，且投影 assistant 文本总长度等于流式 `message_end` 文本总长度（覆盖重复回复）。
- **指标**：harness 内聚合每轮的请求→首 token、工具回传间隔、turn 总时长、错误分类计数；输出 P50/P95/P99，原始 JSONL 与摘要归档到 `docs/research/2026-10-25-m1-loadtest-artifacts/` 供复查。错误分类在 spec 初稿的「硬错误 / 本系统 429 / 上游 429 / 断流」之外增加 `upstream_unavailable`（网关重启窗口内的可重试 5xx / STREAM_INTERRUPTED），以便重启重试与真实故障区分。
- **报告**：落 `docs/research/2026-10-25-m1-load-test-report.md`，含环境快照、方法、原始与扣除口径、通过/不通过判定（对照 §4）。
- **harness 落位**：`tools/loadtest/`（独立 package，TS strict ESM，不混入 gateway/web 构建）。

## Testing Decisions

- harness 是测试工具本身；对其中可单测的纯逻辑（SSE 事件解析、指标分位数聚合、think-time 调度器的确定性）写少量单元测试，先前例为 gateway 的 SSE 解析测试与 web 的 `lib/sse` 解析。
- 最终验收即压测实跑：判定标准取自 §4——50 会话全程稳定、首 token P95 < 3s（扣 TTFB 口径）、工具回传 P95 < 500ms、硬错误为 0、重启后消息不丢不重。
- 不为压测改动任何业务代码；若压测暴露产品缺陷，回填 ticket 修复后重跑。

## Out of Scope

- request_id 全链路 trace（FR-7 / M2）。
- 真实 embedding/rerank 供应商延迟与检索质量。
- 多实例 gateway、亲和路由、冷启动恢复（M2）。
- 限流参数调优（本次仅临时调高排除干扰）。
- web UI 层的并发（harness 不经过浏览器）。

# 用户主动彻底删除会话时，同时删除 pi 会话文件与 sidecar

Date: 2026-10-23

## Status

Accepted（修订 ADR-0008 的「M1 不清理文件」范围）

## Context

ADR-0008 规定 M1 的 pi 会话文件无限保留、清理任务留 M2。但产品现在提供「彻底删除」语义：用户明确要求移除数据。如果只删 MySQL 投影而保留 gateway 磁盘上的完整对话 JSONL，既不符合用户预期，也有隐私风险。

同时，彻底删除涉及两个存储：MySQL 业务行与 gateway 本地文件，跨服务无法用单事务保证。

## Decision

- 彻底删除**只允许针对已归档（archived）会话**，避免删掉正在进行的 Run。
- 顺序：**先删文件，再删业务行**。
  1. Java 校验会话归属与 archived 状态；
  2. 调用 gateway `DELETE /sessions/:id/files`（共享 token + `X-User-Id`）：释放内存 AgentSession（如有）、删除 pi JSONL 与 sidecar；幂等 204；
  3. gateway 成功后，Java 在一个事务里删除 messages → runs → sessions。
- 文件删除失败：返回 502（retryable），业务行保留，用户可重试；不会出现「业务行没了但文件还在」的不可达状态。
- ADR-0008 的「M1 不清理文件」继续适用于普通归档与保留策略；**用户主动彻底删除是唯一例外**。

## Considered Options(被否的备选)

- **只删 MySQL 行，文件留 M2** — 与「彻底删除」语义冲突，隐私风险。
- **先删业务行，再删文件** — 文件删除失败后会话行已不存在，无法重试与校验归属，可能留下孤儿文件。
- **后台 GC 扫描已删除标记** — 最终一致、可重试，但需要新标记列与后台任务，M1 偏重。
- **归档即删文件** — 会让「恢复」失效，违背 Q1 决策。

## Consequences

- 跨服务删除存在短暂不一致窗口（文件已删、业务行未删）；此时会话仍为 archived，用户可重试。
- 需要 gateway 新增内部文件删除端点，并更新契约文档（加法）。
- 彻底删除不可恢复；UI 必须二次确认，并明确提示「历史与引擎上下文都会删除」。
- 普通归档仍保留文件，后续 M2 清理任务继续按 ADR-0008 设计。

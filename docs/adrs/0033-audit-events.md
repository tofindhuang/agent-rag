# 审计日志：元数据、用例边界显式写入、180 天保留

Date: 2026-10-30

## Status

Accepted

## Context

系统目前只有业务账本（`runs`、`exec_records`、`compaction_events`），没有「谁在什么时候改了什么」的记录：

- 改了密码、换了模型供应商的 API key、删了知识库或彻底删除会话，事后都查不到；
- 登录失败、refresh 令牌重用检测这类安全信号只进日志/指标，无法按用户回溯；
- M3 后续的「per-user 配额覆盖」与「数据导出」都需要一个可追责的底座。

FR-7 明确规定 admin 不可查看对话正文、代码与密钥，所以审计必须只记元数据。

## Decision

1. **审计三类事件**：认证与凭证、密钥与配置、破坏性操作。读操作与普通重命名不入审计。
2. **只记元数据**：动作、目标类型/id、结果、操作者、IP、UA、时间；`detail` 是 ≤2 KB 的结构化摘要，**永不**包含正文、文档内容、API key、密码、OAuth token（换 key 只记 `changed`）。
3. **用例边界显式写入**：`AuditService.record(...)` 由 service 层在动作发生时调用，而不是 HTTP filter 或 AOP——只有业务层知道语义化的 `action` 与 `target`。
4. **best-effort**：审计写失败只 warn + 计数器，绝不让业务失败；同时输出一行结构化日志（logger `audit`）作为第二通道。
5. **保留 180 天**：复用现有 `@Scheduled` 每天清理一次；不分区、不归档。
6. **可见性**：用户可在设置页看到自己的安全事件（最近 20 条）；admin 有只读接口与只读页面，可按动作/操作者过滤，但永远看不到正文与密钥。
7. **顺序**：审计先于「per-user 配额覆盖」与「数据导出」，后两者必须留审计痕迹。

## Considered Options（被否的备选）

- **HTTP filter 自动记录所有写请求** — 拿不到语义化 target，且会把读请求也卷进来 → 否决。
- **AOP 注解 `@Audited`** — 需要把参数映射成 target 的元数据，实际比显式调用更难读；本项目规模不需要 → 否决。
- **只写结构化日志、不落库** — 无法按用户回溯、无法在 UI 展示，且日志保留期不可控 → 否决。
- **记录请求/响应正文** — 与 FR-7 冲突，且等于把密钥与对话写进另一个表 → 否决。
- **审计与业务同事务（强一致）** — 会让审计表故障拖垮登录/改密等主流程；审计是观测，不是业务状态 → 否决。
- **永久保留** — 存储与合规成本都不划算 → 否决（180 天后清理）。

## Consequences

- 新增 `audit_events` 表与每日清理任务；写入是异步意义上的 best-effort，极端情况下可能丢一条（有计数器可见）。
- 审计的 IP 复用限流的可信代理解析（ADR-0030），代理后拿到的是真实客户端地址。
- admin 的只读契约扩大一格（新增审计列表），仍然看不到正文/密钥。
- 未来 admin 写操作、配额覆盖、数据导出都必须调用 `AuditService`，否则视为缺陷。

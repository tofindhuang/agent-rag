# 检索质量保障采用「指纹闸门 + 查询调试 + 标注评测」三层

Date: 2026-10-25

## Status

Accepted

## Context

知识库已有摄取计数校验、Qdrant 维度守卫、设置自检（固定查询）和一次 spike 评测，但这些只能证明「管线没坏」：

- spike 的 recall@5 = 1.00 建立在合成模板语料上，真实文档从未复测；
- 用户级 embedding 设置变更会置 stale 并阻断检索，但**部署默认 embedding** 走环境变量，变更后 `source=system` 的用户会静默混用不同模型产出的向量；
- rerank 的效果没有可观测数字，无法判断它改善还是损害了排序。

用户需要回答「我上传的这批文件，embedding 找得回来吗、rerank 排得对吗」，并能在换模型/批量上传后判断质量是否回退。

## Decision

按三层建设，三者互补而非互斥：

1. **模型指纹闸门（被动、持续）**：`kb_documents` 记录 `embedding_model` + `embedding_dim`，摄取成功时写入；检索、自由查询、评测前校验当前生效配置。不一致或 NULL（无法证明）一律抛 `KB_INDEX_STALE`，要求 `reingest-all`。指纹落 MySQL 元数据，不写 Qdrant payload。
2. **查询调试（按需、单条）**：同一候选池输出「向量序」与「当前配置」双列结果，让 rerank 的每一条重排可见；它同时是标注的创建入口。
3. **标注评测（手动、聚合）**：每 KB 维护「问题 → 期望 Passage」标注集，同步运行得到五项指标：当前配置 recall@5 / MRR@5、候选池 recall@10、向量直搜 recall@5 / MRR@5。前三组数字把「embedding 召回不足」与「rerank 排序不佳」拆开——池 recall 低是 embedding/切分问题，池高而最终 recall 低是 rerank 问题。结果落库保留最近 20 次，支持与上次对比。

标注以 `(document_id, seq)` + Passage 文本 SHA-256 标识；重建导致文本变化时标注标记 `rotten`、剔除指标并显式列出，避免静默给出虚假数字。

## Considered Options(被否的备选)

- **指纹写进 Qdrant payload** — 向量侧自带证据，但要重写存量 payload 或整库重建，且校验路径要额外读向量库；MySQL 已有一行一文档的元数据，写入与查询都更轻。
- **指纹 NULL 的存量文档放行、仅标「未知」** — 升级平滑，但对存量文档保留了「静默混用」的缺口，违背闸门「只承认可证明的索引」的初衷；选择升级后强制 `reingest-all`（一次性成本）。
- **评测标注归属于用户（跨 KB）** — 检索按会话绑定单 KB，跨 KB 评测集度量的是产品中不存在的检索形态；且需要额外的库选择语义。
- **评测异步任务 + 轮询** — 几十条标注、并发 4 时约 10 秒内完成，手动场景同步足够；异步需要任务表、状态接口、进度 UI 与重试语义，留到自动门禁阶段。
- **只做标注评测，不建指纹闸门** — 评测数字会被静默混用的向量污染，回归时无法区分「质量下降」与「索引坏了」。
- **只做指纹闸门与查询调试，不做评测** — 无法量化质量，也无法在换模型后判断回退；这是用户最初问题的核心。
- **nDCG@5 作为指标** — 标注是二值相关（命中/不命中），nDCG 退化且不直观；recall@5 + MRR@5 足够。

## Consequences

- 升级后所有存量文档指纹为 NULL，检索被阻断，必须对每个 KB 执行一次 `reingest-all`（原文在对象存储，可重建）。这是有意的硬保证。
- 评测指标只在「已执行且非 rotten」的标注上计算；`complete=false` 的 run 会入库但不作为对比基线，UI 必须显式标注不完整。
- 标注会随 chunker/解析器变化腐化，需要人工重新标注；指纹让腐化变成显式事件，而不是静默错误。
- 换 embedding 模型后应重跑评测；本期只做 UI 提示，不做自动门禁。自动门禁（上传完成/配置保存后后台评测、超阈值告警或阻断）是既定的演进方向，需要任务队列与阈值语义。
- 评测会消耗 embedding/rerank 额度（每条标注一次查询 embedding + 一次 rerank），上限 100 条/KB 将成本封顶。
